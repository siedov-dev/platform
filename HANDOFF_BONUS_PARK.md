
### 🔴 ГЛАВНЫЕ ГРАБЛИ

**1. Новый файл в `public/` → Vite его НЕ видит.** Если пользователь закинул картинку, а сервер уже запущен — он будет отдавать `index.html` (877 байт, `text/html`) вместо картинки, и на фронте будет пусто. **Надо убить процесс и перезапустить:**

```bash
PID=$(netstat -ano | grep ":5173" | grep LISTENING | head -1 | awk '{print $NF}')
taskkill //PID $PID //F
npm run dev
```

Проверить, что файл реально отдаётся:
```bash
curl -s http://localhost:5173/bonus-park/ИМЯ.png | wc -c   # должно быть много байт
curl -s -o /dev/null -w "%{content_type}" http://localhost:5173/bonus-park/ИМЯ.png  # должно быть image/*
```
Просто `npm run dev` поверх работающего — **не помогает**, порт занят старым процессом.

**2. localStorage перебивает дефолты из кода.** Координаты полей читаются так: `localStorage → иначе дефолт из кода`. Если поправить дефолт в коде, а у пользователя в браузере лежат старые значения — он изменений **не увидит**. Ключи: `bonuspark.fields`, `bonuspark.zones`, `bonuspark.covers`, `bonuspark.tilecfg`.

**3. Пользователь смотрит через жёсткий reload** (Ctrl+Shift+R). Всегда просить именно его, иначе кэш отдаёт старые картинки.

React 18 + Vite. Фронт онлайн-казино. Приложение рисуется **в рамке телефона** (~390px шириной), не на весь экран.

`home`, `games`, `bonuspark`, `lunopark`, `ferris`, `sport`, `deposit`, `game`, `promotions`, `bonus`.

Основная работа сейчас — **`bonuspark`** (страница `src/components/pages/BonusParkPage.jsx`).

### Файлы

| Файл | Что делает |

### Экраны внутри BonusParkPage

`view` = `overview` → `grid` (поля) или `park` (список мини-игр).

- **overview** — картинка локации, верх/низ = Park / Fields.
- **grid** (`GridGame`) — главный экран: фон + 6 полей с плитками.
- **park** — список мини-игр (попапы) + Lunapark.

### Поля и плитки

6 полей, **ровно 640 плиток**, нумерация сквозная **с нуля** (согласовано с бэком):

| Поле | Сектор | Сетка | Плиток | cell_id |
|---|---|---|---|---|
| tl | 1 | 10×10 | 100 | 0–99 |
| tr | 2 | 10×10 | 100 | 100–199 |
| ml | 3 | 10×12 | 120 | 200–319 |
| mr | 4 | 10×12 | 120 | 320–439 |
| bl | 5 | 10×10 | 100 | 440–539 |
| br | 6 | 10×10 | 100 | 540–639 |

Раскладка секторов (как рисовал пользователь):
```
1 [tl] [tr] 2
3 [ml] [mr] 4
5 [bl] [br] 6
```
Внутри поля плитки идут слева-направо, сверху-вниз. `cell_id = offset + индекс`.

### Как поля ложатся на фон (ВАЖНО)

Фон — картинка в перспективе. Поля на ней — трапеции. Поэтому каждое поле задаётся **4 углами в процентах** от контейнера, а `perspective.js` строит `matrix3d`, который натягивает прямоугольную сетку плиток на эту трапецию.

**Три независимых набора координат** (каждый по 4 угла на каждое из 6 полей):

| Константа | Ключ в localStorage | Что это |
|---|---|---|
| `DEFAULT_FIELDS` | `bonuspark.fields` | сами плитки |
| `DEFAULT_ZONES` | `bonuspark.zones` | свечение зоны (`Light_field.png`), при выборе поля |
| `DEFAULT_COVERS` | `bonuspark.covers` | обложка-затемнение (`Cover_Field.png` / `_2`) |

Обложки: левая колонка (`tl`, `ml`, `bl`) → `Cover_Field.png`, правая (`tr`, `mr`, `br`) → `Cover_Field_2.png`.

`DEFAULT_TILECFG` = `{ scaleX: 1.15, scaleY: 1.4 }` — насколько текстура плитки увеличена внутри своей клетки (прячет швы, `scaleY` убирает горизонтальные линии). **Не менять без просьбы.**

### Панель ⚙ Setup (инструмент выравнивания)

Живёт в `GridGame`, слева сверху. Нужна, чтобы пользователь сам выставлял геометрию под новый фон.

- В **обзоре**: 3 режима — **Плитки / Свечение / Обложка**. Клик по полю → появляются **красные точки** по его углам → тянешь → сохраняется в localStorage.
- В **зуме**: панель тоже видна (сдвинута ниже кнопки «← Fields»), редактирует **обложку** зумленного поля.
- Кнопка **«Сбросить всё»** — с подтверждением.

**Когда пользователь всё выставит**, он присылает выгрузку, и её надо **зашить в дефолты** в коде. Команда для выгрузки (даёшь пользователю, он вставляет в консоль браузера F12):

```js
copy(JSON.stringify({
  fields: JSON.parse(localStorage.getItem("bonuspark.fields") || "null"),
  zones:  JSON.parse(localStorage.getItem("bonuspark.zones")  || "null"),
  covers: JSON.parse(localStorage.getItem("bonuspark.covers") || "null"),
}))
```
`prompt()` НЕ использовать — он режет длинный текст, уже дважды теряли данные.

### Игровой флоу

1. Клик по полю → поле подсвечивается (свечение зоны).
2. Второй клик → **зум** в поле (перспективный, `transform` на `.gridInner`).
3. Клик по плитке → подсветка (`Light.png`).
4. Второй клик по ней же → **разрушение**: плитка тает + **конфетти**.
5. «← Fields» → выход из зума.

Переходы между экранами — **затемнение** (`.cover` + `coverIn`/`coverOut`): сначала темнеет текущий экран, под чёрным подменяется, потом осветляется. Последовательность важна — пользователь жёстко требовал, чтобы новый контент **не мелькал** до затемнения.

### Эффекты (всё через canvas `Particles.jsx`)

- **Конфетти** — 44 разноцветные бумажки + вспышка. Единственный оставленный эффект (были осколки/пыль/листья — все удалены, конфетти понравилось больше). **Не трогать.**
- **Полёт энергии** (`flyEnergy`) — светящийся сгусток летит по дуге с искристым хвостом.
- **Хук на кромке экрана** (`.screenHook`) — золотая вспышка на верхней кромке при разрушении плитки. Только на **средних и нижних** полях (там колбы не видны).

### Цепочка «плитка → энергия → банк»

Объекты на фоне: **две колбы (резервуара)** `TANKS` и **монета** `COIN` между ними — координаты в процентах.

- **Верхние поля (tl, tr):** колбы видны в кадре → при разрушении плитки сгусток **сразу летит в свою колбу** (tl → левая, tr → правая), колба вспыхивает. Хук на кромке НЕ показывается.
- **Средние/нижние:** колб не видно → при разрушении хук на кромке; **при выходе** из сектора летят **2 сгустка в колбы + 1 в монету**.
- **Верхние при выходе:** только **1 сгусток в монету** (в колбу уже улетело во время игры).

Колбы и монета **не светятся постоянно** — только вспышка в момент попадания (`.tankFlash`, `.coinFlash`). Пассивную пульсацию убрали по просьбе.

### Кривые анимаций

`easings.js` — оставлены только **easeInOutQuart** и **easeInOutExpo** (руководство выбирает между ними). Переключатель — на главной странице (`EaseSwitcher`), пишет CSS-переменную `--ease`, её используют зум и переходы.

**Затемнение-переход НЕ использует `--ease`** — у него своя мягкая `ease-in-out`, потому что с резкими кривыми оно «моргало».

## Производительность (важно, но потом)

Целевая аудитория — **слабые телефоны, медленный интернет**. Решили: **сейчас вставляем всё как есть**, чтобы увидеть картину целиком, а оптимизируем в конце, по одному элементу.

Что уже известно и ждёт своей очереди:
- Мёртвые ассеты в `public/bonus-park` (~3.3 МБ): `field_tiles.png`, `Bg-web.jpg`, `5350316627389521175.jpg`, `Cover_Field_3.png` — не используются, можно удалять.
- `Bg.png` (25 МБ) и `bg_2/bg_3.png` — старые фоны, тоже кандидаты на удаление.
- Пульс свечения использует `filter` (дорого для слабых GPU) — можно упростить до `opacity`.
- 640 плиток = ~2000 DOM-узлов. Статичны, но если будут тормоза — переводить поля на `<canvas>`.
- **Колесо обозрения** (`public/ferris/`, 6 атласов 4096×4096, 25 МБ, ~400 МБ в памяти) — в текущем виде для слабых устройств неподъёмно. Художникам передано: кадр ~400×430 вместо 819×878, 60 кадров вместо 120, атласы **не больше 4096** (8к не отрисуется на многих мобильных GPU), trim включить, WebP вместо PNG. Сейчас говорят, что переделают через **Lottie** — тогда вопрос закрыт.

Инструмент для картинок (sharp) стоит в scratchpad, ImageMagick в системе НЕТ (`convert` в PATH — это виндовая утилита файловой системы, не картиночная):

## Требования к ассетам (передано художникам)

- Фоны: **9:16 или выше (19.5:9, 20:9)**, важное в центре, края под обрезку. JPG/WebP, не PNG. ≤300–500 КБ.
- Прозрачные элементы: WebP/PNG, обрезать пустые поля вокруг.
- Всё рисовать в ~2× от того, как показывается на экране (рабочая ширина телефона ~400px).
- Покадровые анимации: атлас ≤4096, минимум кадров, trim, WebP.

⚠️ Если сменят пропорцию фона — **всю геометрию придётся выставлять заново**. Пользователь про это знает.
